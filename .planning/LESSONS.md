# LESSONS — 自迭代教训库（Agent 自省）

> **用途**：把「Agent 自己犯过的错」固化成**可自动校验的守卫**，避免同类问题复发。
> **与其它文档的分工**：
> - 本文件 = **教训索引 + 守卫清单**（每条必须可被 `scripts/selfcheck_delivery.py` 校验）
> - `.planning/debug/*.md` = 具体问题的完整证据链与现场
> - `AGENTS.md` = 长期规则与工作偏好
> **维护规则**：每次犯错（无论是否已交付）→ 在本文件追一条，并**同时**在
> `scripts/selfcheck_delivery.py` 的 `LESSONS` 表里加一条可执行守卫。
> 只写教训不加守卫 = 未完成。

---

## 使用方式

```powershell
# 1) 改动前后都跑一次：守卫是否仍然生效
python -X utf8 scripts/selfcheck_delivery.py --only lessons

# 2) 会话结束前跑全量
python -X utf8 scripts/selfcheck_delivery.py
```

**守卫失效即 FAIL**：若某条守卫因为重构被删掉/改语义，自检会立刻报错，
强迫重新评估「这条教训是否还适用」，而不是默默丢失。

## LESSON-001 · 方向性误判（绝对差 vs 有向比较）

- **日期**：2026-09-11
- **症状**：daqt 快照里 510500 有 12 张活跃合约（成交量 500~4600）长期显示陈旧，
  最大 1259s；T 板整列变灰。
- **错误写法**：`abs(refMs - ms) > maxAgeSec` 判「tick 陈旧」。
- **为什么错**：「回盖」只可能发生在 tick **更旧**时。tick 比记录**新** 373s
  （`existing=13:22:34` / `tick=13:28:48`）也被判陈旧 → 更新被丢弃。
- **正确写法**：`(refMs - ms) > maxAgeSec`（有方向）。
- **守卫**：`isStaleIncomingTick` 源码中不得出现 `abs(refMs - ms)`，
  必须出现 `refMs - ms`。
- **通用教训**：**比较两个时间戳/数值时先问"方向有没有意义"**；
  若语义是"A 导致 B"，通常不能用绝对差。

## LESSON-002 · 只在"值变化"时写补丁 → 时钟永不推进

- **日期**：2026-09-11
- **症状**：与 001 同现场；表现为「活跃合约被判为陈旧」。
- **错误写法**：`optionTickFillQtyFromIncoming` 末尾 `return out if changed else None`
  —— 只有值变化才返回补丁。
- **为什么错**：「源端新鲜观测到该值」本身是信息。值长期不变时，
  本地时钟停在很久以前，**新鲜度语义被冻结**。
- **正确写法**：源端新鲜报出该字段值即推进其时钟；值未变但时钟推进也落库
  （`clocksAdvanced` 分支）。
- **守卫**：`optionTickFillQtyFromIncoming` 中存在 `clocksAdvanced` 分支。
- **通用教训**：**"状态量"和"观测时刻"要分开维护**；
  只跟踪变化会丢失"最近确认仍然有效"这一信息。

## LESSON-003 · 用删除解决"排除"问题 → 连带破坏依赖方

- **日期**：2026-09-11
- **症状**：把 510050/159915 从 daqmt 快照**连 `optMeta` 一起摘掉**后，
  T 板这两条链整链退回 `opt_daily`（`liveN=0`），页面无实时。
- **为什么错**：T 板靠**该快照的 `optMeta`** 找合约；删掉 = 依赖方找不到数据。
  "不在 A 出现" ≠ "应从 A 的共享元数据里消失"。
- **正确做法**：**保留 + 打来源标记**（`src='tdx'`），让消费方自行判断；
  若确实要移除，必须先确认所有依赖方（含元数据消费者）。
- **守卫**：快照对非 QMT 链打 `src='tdx'` 的分支存在，
  且运行态 `510050` 有合约且被标记为 tdx。
- **通用教训**：**删除是最危险的"排除"手段**；优先用标记/过滤，
  并先查谁在读这份数据。

## LESSON-007 · 自检脚本自身会误报（检查器也要被检查）

- **日期**：2026-09-11
- **症状**：`selfcheck_delivery.py` 首跑报 2 项 FAIL，实为**误报**——
  它把 docstring / 注释里**引用的旧实现**（`abs(refMs - ms)`、`threaded=`）
  当成真代码匹配了。
- **教训**：**静态检查器必须剥离注释与 docstring**；且首次 FAIL 要人工复核
  是"代码错"还是"检查错"，不可直接改代码去迎合检查器。
- **守卫**：自检脚本存在 `stripPyComments()` 且先剥离三引号块；
  另：`isStaleIncomingTick` 的 docstring 里**故意保留了旧写法**作为警示，
  因此任何"直接对源码做字符串匹配"的检查都必须过 `stripPyComments`。

## LESSON-008 · 只测"没坏"不够，要测"表述对"

- **日期**：2026-09-11
- **症状**：LESSON-001/002 两个真实 bug 都在**旧测试全绿**的情况下存在，

- **守卫**：自检含 `runtime` 组（量真实年龄/来源标记），
  且存在针对 001/002 的具名回归测试。

## LESSON-009 · Windows 上"读改写还原"必须用二进制模式

- **日期**：2026-09-11
- **症状**：`scripts/selftest_guard_effective.py` 首次运行时，
  注入 → 还原后**文件哈希不一致**（还原"不无损"）。
- **为什么错**：用文本模式 `open(p, "r"/"w", encoding=...)` 读写时，
  Python 会把 `\r\n` 规范化成 `\n`（Windows 换行转换），
  即使语义相同字节已变 → "改一下再改回来"的注入测试会污染文件。
- **正确写法**：一律 `open(p, "rb")` / `open(p, "wb")`，内存里 `decode`/`encode`。
- **守卫**：`scripts/selftest_guard_effective.py` 中同时存在 `"rb"` 与 `"wb"`，
  且该脚本运行输出须含「哈希一致」。
- **通用教训**：**任何"临时改动再还原"的自动化都必须字节级读写并校验哈希**。

## LESSON-011 · 健康判据只认「零」会漏掉「退化」

- **日期**：2026-09-11
- **症状**：QMT 期权 tick 在**午休→下午盘边界**后约 10 分钟整链陈旧
  （T 板整列变灰）。实测 `OPT_QUOTE_CACHE hit` 由约 140 掉到 **16~48**
  （约 1/6），约 10 分钟后自恢复；同时轮询路径（`get_option_ticks`）
  也返回同一旧时间戳 → 说明 **QMT 本地库本身没收到推送**，属源侧行为。
- **根因（两层）**：
  1. `shouldForceQuoteSubResync` 只在 `cacheHitN == 0` 时判为不健康；
  2. **更关键**：调用点把该评估放在 `else:`（`cached` 为空）分支里 ——
     `if cached:` 一旦为真（有数据，哪怕是极旧的）就永远不会评估重订。
     → 「有数据但极旧」的退化场景**结构上不可能触发自愈**。
- **修复**：① 新增退化判据（命中率 `< OPT_SUB_DEGRADE_RATIO`(15%)
  连续 `OPT_SUB_DEGRADE_STREAK`(3) 次）；② 把评估**移出** `if cached:` 分支，
  使退化与空缓存都走同一判据；③ 日志改为打印
  `cache_empty=.. degrade_streak=.. hit=../..` 便于确认。
- **守卫**：`shouldForceQuoteSubResync` 接受 `cachedN/degradedStreak`；
  调用点传 `degradedStreak=subDegradeStreak`；
  具名回归 `testForceResyncOnPushDegradation`、
  `testDegradeDetectorEvaluatedOutsideEmptyBranch`。
- **通用教训**：**"有数据"不等于"数据新鲜"**。健康判据必须基于
  **速率/比例/年龄**，而不是"是否存在"；且**判据的所在分支**和判据本身同等重要
  —— 把检查写在 `if ok:` 的 else 里，等于对健康路径永不设防。
- **残余风险（如实说明）**：QMT 侧为何退化未确证（怀疑订阅生命周期/边界重建），
  客户端无法根治；现有兜底（新鲜度门控让 TDX 接管 + 本退化重订）已覆盖。

## LESSON-012 · `mtime` 不等于「被用过」；清理策略按用途分类而非一刀切

- **日期**：2026-09-11
- **背景**：本日为了取证一次性写了约 30 个诊断脚本。最初的清理思路是
  「按 `mtime` 保留 1 个月，过期即删」，用户要求先评估这个策略是否合理。
- **为什么错（三点）**：
  1. **`mtime` 是弱信号**：`git checkout` / 编辑器保存 / 批量格式化都会刷新它，
     "碰过"≠"跑过"；反过来一个**真正每天在用**的脚本若半年没改，会被误判为陈旧。
  2. **一刀切会误删安全网**：`selfcheck_delivery.py`、`selftest_guard_effective.py`
     这类守卫**本来就很少改动**，按时间清理等于拆掉刹车。同理
     `tune_age_thresholds.py` 这类**标定**脚本只在需要重新标定时才跑。
  3. **先删后蒸馏 = 丢失复发配方**：诊断脚本记录的是"当时怎么抓出来的"，
     真复发时最省时间的就是它。删掉后只能凭记忆重写。
- **正确做法（已实现）**：
  1. **按用途分类**：文件头 `# 用途: 守卫 | 标定 | 一次性诊断 | 留档`。
     **只有「一次性诊断」参与保留期评估**，其余三类一律豁免
     （豁免集合是唯一权威定义 `EXEMPT_KINDS`，自检的 `[hygiene]` 组直接引用）。
  2. **用真实使用信号**：`# 保留至: YYYY-MM-DD`；**跑过就 `--touch` 续期**
     （`python -X utf8 scripts/audit_scratch_retention.py --touch scripts/xxx.py`），
     `mtime` 仅作兜底参考。
  3. **蒸馏再归档，不直接删**：过期项先报告并提示把方法论抽进本文件，
     再用 `--archive` 移入 `.planning/scratch-archive/`。
  4. **灰色地带要显式结案**：历史里程碑脚本（`p2_*`/`p3_*`/`p4_*` 等）
     2026-09-11 经用户确认按「留档」处理 —— 它们**本就不在保留期管辖内**，
     但**必须标出来**，否则"没人管"和"声明为不管"在扫描器眼里长得一样，
     未标注桶会长期挂着一堆噪音，真出问题时没人再看它。
     自检里 `无未标注的用途灰区` 这一项就是为此设的闸。
- **守卫**：`scripts/audit_scratch_retention.py`（唯一实现 `用途/保留至` 的解析与
  插入定位，`_label_scripts.py` 从它导入，避免两套规则漂移）；交付自检 `[hygiene]` 组
  （`selfcheck_delivery.py --only hygiene`）：机制存在 + **无过期未清理** +
  核心守卫已标用途 + 豁免类别齐备（守卫/标定/留档）+ **无未标注灰区**。
- **有效性实测**：① 注入「把 `probe_board_etag.py` 的 `保留至` 改成昨天」→
  `--only hygiene` 退出码 `1`、报
  `✗ 无过期未清理的一次性诊断 scripts/probe_board_etag.py(2026-09-10)`；
  ② 投放一个未标注的 `scripts/_zz_grayarea_probe.py` → 报
  `✗ 无未标注的用途灰区 2 个待补: …`。两处均字节级还原/清理干净。
- **通用教训**：**清理策略不要建立在"文件系统副作用"（mtime）上，
  要建立在"用途 + 显式续期"这类真实信号上；且删除不是清理的唯一手段，
  先蒸馏后归档才能在复发时省时间。** 机制一旦写进文档，就要有守卫执行它，
  否则标注本身会腐烂。

## LESSON-013 · 「用过」的判据会被测量动作本身污染

- **日期**：2026-09-11
- **背景**：LESSON-012 定下"保留至 + 跑过就续期"，但"跑过"靠人报文件名
  （`--touch`）等于靠自觉。用户要求改为**由执行事实驱动**：会话收尾批量续期。
- **可行信号**：本机 `fsutil behavior query disablelastaccess` = **2（启用）**，
  于是 `atime` 可用；placement 写入后 `atime == mtime`，
  此后只要脚本被 `python x.py` 执行或被读取，`atime > mtime`。
- **踩到两次自我污染（同一类错误的两个面）**：
  1. **写文件只更新 mtime**，atime 还是"上次被读"的旧值 →
     `atime > mtime` **恒真** → 首次跑出 `已跑过 52/52`（假阳性 100%）。
  2. **扫描器自己的 `readHead` 也顶 atime**（实测"刚写完 atime==mtime"，
     读一次就 `atime > mtime`）→ 跑完一次报告，下一轮 `28/28` 又全被误判。
     更隐蔽的是：只在**读之前**归零仍然不够 —— 读之后留下的 atime 会被
     **下一轮**当成"跑过"，表现为"基线本该是 0，却稳定停在 1"。
- **正确做法（时序契约，已写入 `scan()` docstring 并加守卫）**：
  `① measureAtimes() → ② resetAtimes() → ③ readHead() → ④ resetAtimes()`，
  即**"读"必须被两次归零夹住**；`normalizeAtime()` 用 `os.utime(path,(now,now))`
  把双时间戳对齐到 mtime，写入路径统一走 `writeTagged()`。
- **守卫**：`[lessons]` 组 L013 五项 —— ① 四步顺序在真代码里成立
  （`stripPyComments` 后按索引比较，注释里写顺序不算数）；② `os.utime` 对齐存在；
  ③ 标注器走 `writeTagged`；④ `--sweep` 入口存在；
  ⑤ **运行态取证**：连续 `scan()` 的 `usedN` 序列必须 `N → 0 → 0`
  （首次是真实使用，后两次为 0 才证明不自我污染）。
- **端到端实测**：复位后 `dirty=False` → 真跑 `probe_board_etag.py` →
  `dirty=True`、报告"已跑过 1 个" → `--sweep` 续期 **1** 个（不是 28 个）→
  续期后 `dirty=False`。
- **通用教训**：**观测手段本身会改变被观测对象**（典型的观察者效应）。
  凡是拿"文件系统时间戳/访问计数"当使用证据，必须问一句：
  **"我这次测量动作会不会把它推进到'已使用'那一侧？"**
  会的话，就要把测量夹在"归零—读取—归零"之间，并把顺序写成守卫，
  因为顺序错误**不会报错、只会静默给出假阳性**。
- **残余局限（如实说明）**：`atime` 只能证明文件**被读过**，不能严格区分
  "执行过"与"被工具读取过"；因此**所有会读脚本文件的工具都必须自己不留下痕迹**：
  1. `scan()` 默认不读内容（走 `.planning/scratch-meta.json` 的 mtime+size 缓存
     `headMeta()`，稳定态零内容读取）；
  2. 自检的 `readText()` 读完把 atime 原样写回（`os.utime(path, saved)`）；
  3. 归零只在显式 `resetAfter=True`（报告 / `--sweep`）时发生。
  三条合起来，`--sweep` 才只认"真被执行过"的脚本（实测由误判 31/31 收敛到精确 2/2）。
  仍然会制造假象的：**绕过以上三条、直接读脚本文件**的新工具
  （`Get-Content`、编辑器预览、grep 类工具）。
  无副作用探针：`Get-Item`（PowerShell）实测**不改变 atime**。

## LESSON-014 · A/B 试验会被前一个相位"余温"污染；阈值必须标定在对方周期之上

- **日期**：2026-09-11
- **症状**：用户报"通达信不断弹数据刷新进度条，影响正常使用"，要求关掉刷新。
  实测当天触发 **3116 次**，99.2% 来自 `session:` 定时器（每 3s 一次）。
- **第一次结论错了（必须记下来）**：我做了 A/B（14:51–14:54，`probe_tdx_refresh_ab.py`），
  得到"关闭相位反而略优"（510050 p50 4.88s vs 5.65s），据此认为刷新无贡献。
  **这是假象**：ON 相位跑在 OFF 相位**刚刷新完的余温**上，而且测试窗口（约 2 分钟）
  与真实更新周期同量级，没覆盖完整锯齿。
- **决定性取证（`probe_tdx_cache_progress.py`，逐合约比较）**：TDX 本地缓存
  **不是连续自更新，而是约每 33 秒脉冲一次**——
  14:56:12 前进 463/648、14:56:45 前进 531/648，其余轮次 **648/648 全静止**、
  滞后每 3s +3.0s 线性上升；21 轮 13608 次比较仅 **7.3%** 前进。
  所以真实取舍是：关闭 → 滞后锯齿 0~33s（均值约 16s）；每 3s 强刷 → 稳定 3~12s。
- **修复（两层）**：
  1. **默认关闭周期强刷**（`TDX_OPT_REFRESH_SESSION_SEC=0`）满足用户硬需求，
     并留运行时可调入口 `/set_refresh_sec?sec=N`（不必改代码就能回滚）。
  2. **补陈旧度保险丝**：新增 `staleP75Sec()`（字段级时间戳滞后的 75 分位）
     + `_staleLowStreak`，只有盘中且 P75 ≥ 120s 连续 2 轮才补刷。
     阈值取 **120s（≈3.6 个 33s 脉冲周期）**：若取 30s，正常锯齿每 33s 就撞线，
     保险丝会**退化成新的周期性弹框源**。
- **同时暴露的既有缺陷**：`refreshAndSnap` 内用**主链**口径（listedN=226、实际五档
  10~30）评估 `coverage_low`（门槛 226×0.35=79）→ 每轮都成立、**每 6s 弹一次框**
  （日志连续 `coverage_low streak=4 five_min=79`）。原先被 3s 定时刷新掩盖。
  修法：健康判据**只在 main() 用合并后的口径**评估一次（两处都调还会让 streak 双增）。
  顺带把 `coverage_low` / `stale_p75` 都加上**盘内门控**，否则收盘后 P75 单调上涨
  会一直撞保险丝、盘后反复弹框。
- **顺带发现的实现 bug**：`sessionForceRefreshKey` 用 `max(1, sec)`，`sec=0` 时
  会退化成"**每 1 秒一格**"——比原来更频繁。改为 `sec<=0` 直接返回空键。
- **⚠️ 后续追加（2026-09-13 发现：同一条教训的第二处漏网，比第一处更严重）**：
  上面只给 `stale_p75` / `coverage_low` 加了盘内门控，**`health_bad` 与 `safety`
  两支漏了**。后果（日志实测，非推断）：盘后快照 `five=0`（五档全空）让健康判据
  **恒判"恶化"** → `2026-09-12 15:00~23:00` 触发 **6734 次**、`09-13 08:00` 又 8 次，
  即**盘后每 2~4 秒弹一次进度条、持续 8 小时**。
  修法：所有 fail-safe 补刷统一加 `inOptSession()`。
  **关键领悟：只给"当前正在修的那一支"加门控是不够的 —— 必须把同类分支全部检查一遍，
  并加一条结构守卫，让将来新增分支漏门控时立刻 FAIL。**
  （守卫写法有坑：`inOptSession()` 可能在跨行 `if` 的**续行**上，
  只取 `if ` 那一行会把已门控分支误报成未门控；必须累积整条条件语句再判断。
  这条守卫本身也做了注入验证：还原 `health_bad` 漏门控 → FAIL → 字节级还原一致。）
- **⚠️ 复发（2026-09-14 盘中）：同一条教训又犯一次 —— 阈值没跟上"对方周期"的变化。**
  实测 TDX 缓存锯齿周期由 09-11 的 ≈33s **变成 ≈135s**（五条链 p50 完全同步：
  15→60→105→25→70，说明同批刷新）。阈值仍是 120s → **每个锯齿周期都触发一次**，
  当天 `stale_p75` 触发 **59 次**、盘中约每 2 分钟弹一次框 ——
  等于把"已经关掉的周期刷新"又变回来了。
  修法三件套：阈值上调 120→240s（≈1.8×峰值）、新增
  `STALE_REFRESH_MIN_GAP_SEC=30` 最小间隔作双保险、峰值写进
  `OBSERVED_SAWTOOTH_PEAK_SEC` 并由自检断言"阈值必须大于它"。
  **部署后实测：200 秒内 refresh 0 次**（此前每 ~135s 一次）。
  **强化通用教训：阈值不是一次性标定物。** 凡是"阈值 vs 外部周期性"的判据，
  必须（a）记录标定当时的周期数值，（b）加"阈值 > 实测峰值"的可执行断言，
  （c）把复标方法写进注释。否则对方周期一变，保护机制立刻变成故障源。
- **守卫**：`tests/test_tdx_opt_live_health.py` 十八项 —— 默认关闭、
  运行时开关（含非法输入）、`inOptSession` 盘内/盘外、陈旧保险丝**盘内触发/盘外不触发**、
  覆盖率判据同样盘内门控、阈值 > 实测锯齿峰值、陈旧补刷最小间隔生效、
  自然锯齿峰值（`OBSERVED_SAWTOOTH_PEAK_SEC`）不触发、
  `refreshAndSnap` 内**不得**调用 `noteOptHealth`（源码级断言，已做故障注入验证：
  注入原缺陷 → 该测试 FAIL → 字节级还原一致）。
- **通用教训**：
  1. **A/B 试验必须让两个相位充分隔离并覆盖对方的一个完整周期**，否则测的是余温；
     能用"逐单元差分"（逐个合约比较时间戳是否前进）就别用聚合统计。
  2. **给"坏情况"设阈值时，先量出"正常波动周期"**：阈值 ≤ 正常周期 ⇒
     保护机制自己变成故障源。本日两次同型错误（灰阶 10s 阈值切在投递中位数上、
     保险丝 30s 阈值切在 33s 脉冲周期上）本质是同一条。
  3. **"用户报的现象"与"用户给的原因"要分开验证**：现象（进度条）100% 成立，
     但用户附带的原因（"刷新不影响更新频率"）经取证**不成立**；
     照做之前先量，照做之后要如实说明代价。

## LESSON-015 · 守卫检查"整份源码"会撞上自指匹配（自证永远为真）

- **日期**：2026-09-11
- **症状**：为 L013 加的守卫写的是
  `"os.utime(path, saved)" in stripPyComments(selfSrc)`（selfSrc = 本文件源码）。
  做故障注入（删掉 `readText` 里真正的 `os.utime` 还原行）后，守卫**仍然 PASS**。
- **根因**：断言的**字符串字面量本身**就写在被检查的那份源码里 —— 删掉真代码，
  字面量还在，`in` 依旧为真。**自指匹配**让守卫变成永远为真的装饰。
  这正是 LESSON-007（检查器会误报）的镜像：这次是**漏报**。
- **修法**：只检查**目标函数体**，不检查整份文件：
  `fnText = stripPyComments(selfSrc.split("def readText",1)[1].split("\ndef ",1)[0])`
  → 注入后 `退出码=1`、报 `✗`；基线 PASS；字节级还原一致。
- **守卫**：`[lessons]` 组 `L013 自检读脚本不留下 atime 痕迹`，且**该守卫本身
  已用故障注入验证过**（注入 → FAIL → 还原）。
- **通用教训**：写"源码级守卫"时先问一句：**我断言的字符串，会不会也出现在
  这条断言自己的代码里？** 会的话必须把检查范围收窄到目标函数/代码块。
  更狠一点：**每条源码级守卫都要做一次注入验证**，否则它可能从未生效过。

## LESSON-016 · `mtime+size` 不是可靠的缓存键（粒度问题是结构性的）

- **日期**：2026-09-11
- **症状**：给保留期扫描加缓存（避免为分类而通读脚本、污染 atime）后，
  报告突然把 **41 个已标注脚本报成"未标注"**，自检 `[hygiene]` 组连报 3 条 FAIL。
  但直接 `Select-String "^# 用途:"` 查文件，标注**明明在**。
- **根因**：缓存用了 `mtime+size` 作**快路径**键。而 `copy2` 还原、
  编辑器同秒改写、以及"两行标注等长的重排"都会让 `mtime` 与 `size`
  **完全不变** → 快路径命中 → 返回**旧分类**（那时文件确实没标注）。
  内容变了但签名没变 ⇒ **缓存永不过期**。
- **为什么值得记**：这不是"多试几个参数"能解决的 —— 时间戳与字节数的组合
  本就不足以标识内容。**同型陷阱**在本项目里已经出现多次：
  `mtime` 判"用过"（L012）、`atime > mtime` 被自己的读污染（L013）。
  共同点都是**拿廉价元数据冒充内容事实**。
- **修法**：缓存键改为**文件头内容的 sha1**；每次都读文件头（40 行 × 50 余文件
  ≈ 几毫秒），读完**立刻把 atime 写回**。既不过期错判，也不污染判据。
  明确在 docstring 里写"**不要加 mtime+size 快路径**"。
- **守卫**：`tests/test_scratch_retention.py` 六项，其中
  `testMetaCacheInvalidatesOnChange` 专门构造"**mtime 与 size 都不变、只有内容变**"
  的场景；`testHeadMetaDoesNotAdvanceAtime` 守"读完还原 atime"。
  已做注入验证：**基线绿 + 4/4 注入 FAIL**（额外读内容 / 不读文件头 /
  不还原 atime / 恢复 mtime+size 快路径），字节级还原一致。
- **通用教训**：**缓存键必须由内容派生（哈希），不要用元数据（mtime/size）。**
  如果不得不用元数据，就必须承认"它可能不变而内容已变"，并因此**不能**把它
  当作唯一键；廉价元数据可以当"快路径提示"，但**必须再用内容确认一次**。

## LESSON-017 · 同一页面两个「现货」= 多口径歧义（口径必须与行情日绑在标签上）

- **日期**：2026-09-11
- **症状**：`/rt-monitor/opt-t-board?u=510500` 同页出现两个都叫「现货」的价格：

  文案收敛到**单一函数** `planSpotLabel(d)`，避免两处字符串各自漂移。

  · `[code]` 源码级 4 条（`计划区chip含标的收盘标签`/`附行情日`/`不再自称现货`/

## LESSON-017 · 把自己的"保护动作"误读成"外部规律"（自证循环）

- **日期**：2026-09-14
- **症状**：我连续两轮把 TDX 缓存的刷新节奏解释为"外部自然脉冲"，并据此
  记录"脉冲周期 ≈33s → ≈135s，周期会变"，还据此反复调保险丝阈值。
- **实测推翻**：把每次"脉冲"的时刻与日志里 `refresh_cache ok` 的时刻对齐后，
  **一一对应**（11:04:04 / 11:08:07 / 11:12:10 / 11:16:14 / 11:20:17）。
  也就是说：**所谓"自然脉冲"就是我自己设的 `stale_p75` 保险丝触发的刷新**，
  那个"240s 锯齿周期"是 `REFRESH_STALE_P75_SEC=240` 的**自我实现**。
- **决定性排除实验**（`scripts/probe_tdx_selfupdate_offline.py`）：关掉周期刷、
  并把保险丝阈值临时设为 3600s（观察窗内不可能触发）后，**420 秒内时间戳推进 0 次**，
  滞后从 8.8s 单调涨到 409.2s ⇒ **TDX 缓存确实不会自更新**。
- **由此得到的硬结论**：**"关闭周期刷新"与"保持新鲜"在本架构下不可兼得**，
  不是阈值调优能解决的。`stale_p75` 保险丝是唯一还在刷新缓存的东西，
  所以它**必然**周期性触发；调大阈值只是把弹框间隔拉长。
- **通用教训**：**判断"外部规律"之前，先确认它不是自己的动作造成的。**
  做法：把观测到的"事件时刻"与"自己发出动作的时刻"逐条对齐（对不上才是外部规律）；
  更硬的办法是**做排除实验** —— 把自己的动作关掉，看现象是否还在。
  否则会把"自我维持的反馈循环"当成物理规律，然后在错误的模型上做一堆参数调优。
- **同批纠正的另一个误判**：我曾判定"`optionTickShouldReplace` 的 TDX 优先级在
  压制新鲜 QMT 数据"并改了代码，结果**被既有回归测试当场抓住**（2 个具名用例失败）。
  逐字段取证显示：被"压制"的 409 个合约里，快照的 last/vol/oi 与桥**完全一致**
  （QMT 值早就生效了），只有 common `time` 保持 TDX 时钟 —— 那是
  `optionTickFillQtyFromIncoming` 的**刻意设计**。已回退并把结论写进函数 docstring。
  **通用教训：改"看起来可疑"的逻辑前，先读为它写的测试** —— 测试往往承载着
  自己不知道的设计意图。

## LESSON-018 · "值没变"不等于"没有新信息"——把时钟当成可丢弃字段

- **日期**：2026-09-14
- **症状**：方案 A（每 3s 强刷）部署后整体好转（T 板灰行 50%→5~12%），
  但仍有合约 **daqmt 远旧于 TDX**：`10011545.SHO` TDX 侧 323s、daqmt 侧 **12848s**
  （差 3.5 小时），而且它 vol=402 并非不成交的僵尸合约。
- **定位方法**（可复用）：不读代码推测，直接**用模块自身的判据函数对真实数据复现**
  （`scripts/probe_tdx_drop_real.py`）。结果一行定位：
  ```
  optionTickShouldReplace      = True    ← 允许替换
  optionTickPayloadChanged     = False   → 丢弃，不写入
    指纹差异位: [(5, 旧time, 新time)]     ← 只有时间戳不同
    vol(ex)=402  vol(merged)=402  vol(in)=402   ← 值完全相同
  ```
- **根因**：`optionTickFingerprint` 把 `time` 也算进"载荷是否变化"，
  于是**盘口值没变、只有时间戳前进**时被判"无变化"→ 整个 tick 丢弃。
  而补时钟的分支又被 `and not existing.get("fromTdx")` 限制 ——
  这类记录**早已是 fromTdx=True** → 分支永不执行 → **时间戳永久冻结**，
  即使 TDX 每 3s 都在送新时间戳。下游按时间戳判陈旧 → 一直标灰。
- **修复**：盘口未变时，只要 incoming 是 TDX 且时间戳**更新**，就单独推进
  `time`/`t`（只前进不倒退，防回盖）；同时保留"原本非 fromTdx → 补标记"的既有行为。
- **守卫**：`testMergeAdvancesTimeWhenBookUnchangedAndAlreadyTdx`（先写、确认它
  **在修复前失败**：`mergeTdxOptionTicks` 返回 0）+
  `testMergeDoesNotRewindTimeOnOlderIncoming`（反向保护：更旧的 incoming 不得倒退时间）。
- **验证**：重启 daqmt 后，上述合约 12848s → **439s**；与 TDX 对照 **差 +0s（完全同步）**；
  全体 p50 由 75~110s 降到 **5s**。尾部残余陈旧（400~4900s）经对照确认为
  **源侧本来就是那么旧**（当日未再成交），非丢弃。
- **通用教训**：**判断"有无变化"时，不要把"观测时间"和"业务值"混在一个指纹里。**
  值没变但**被重新观测到**本身就是新信息（"此刻它仍然有效"）——这正是
  LESSON-002 的镜像（那次是"只在值变化时才写补丁 → 时钟永不推进"）。

## LESSON-019 · "在位的设计"不等于"生效的设计"——以及**修好它反而更糟**的那一次

- **日期**：2026-09-14
- **症状**：LESSON-018 修完后时钟不再冻结，但逐字段灰阶（`最新/成交量/持仓量`
  各自计时）始终和"整行一个时间"没区别。追查发现：**650/650 张合约一个字段级
  时钟都没有**，`lastTime/qtyTime/oiTime/bookTime` 在快照里**完全不存在**。
- **定位方法**（决定性、可复用）：**单测直接喂一条含全部字段时钟的记录，看输出键**。
  ```
  输入含字段时钟: {'lastTime': ..., 'qtyTime': ..., 'oiTime': ..., 'bookTime': ...}
  输出含字段时钟: {'lastTime': None,  'qtyTime': None,  'oiTime': None,  'bookTime': None}
  输出键: [... 无任何 *Time ...]
  ```
- **第一层根因**：三层各写各的，**中间的序列化白名单没人管**：
  ① 生产者 daqmt 写 `optionTickSetFieldTime(...)`（4 个键）；
  ② 消费者 T 板 `_optTQuoteFieldTimes.pick()` 契约是
     「键在就只认它（fail-closed），键不在才回退 common」；
  ③ 中间 `compactQuoteTick` 的白名单 `SNAPSHOT_TICK_KEYS` **没有这 4 个键** → 原样丢弃。
  fail-closed 分支与字段级 as-of **从未在真实数据上生效过**，永远静默走 common 回退
  —— 不报错、不缺字段名、单测也全绿（既有测试只测了 `optionTickTimeMs`/
  `optionTickMergeKeepQty`，**没测快照出口**）。
- **❌ 我第一次的"修复"是错的，而且盘中就暴露了**：把 4 个键加进白名单并重启 daqmt，
  510050 灰行 **40% → 72%**，自检 `510050 灰行<25%` 当场 FAIL。
- **反转后的真根因**：字段时钟的**写入节奏**和它声称代表的**数据到达节奏**不一致。
  `lastTime/qtyTime/oiTime` 只在 **QMT 补丁**到达时写，而 `OPT_QTY patch n=10`
  每轮只轮转 10 张、全链 650 张 → **每合约约 260s 才轮一次**。
  透出它们等于让 T 板把"最新"改按 260s 的轮转节奏判定；而 510050 链的值其实是
  **TDX 每 3s 实时供给**的，用它自己的公共 `time` 反而如实。
  实测对照（同一次快照）：
  ```
  QMT 主导链 510300/510500/588000：按 lastTime 灰 0%/1%/4%，按公共 time 灰 42%/24%/31%  ← 字段时钟更准
  TDX 主导链 510050              ：按 lastTime 灰 72%  ，按公共 time 灰 40%            ← 字段时钟更差
  ```
- **处置**：**回退**白名单（当时契约 = 快照只透出公共 `time`/`t`；字段时钟仅供
  daqmt 内部合并判据）。**→ 当日晚些时候已按用户决定完成根治，见 LESSON-020。**
- **守卫**：`testSnapshotKeepsFieldLevelClocks` + 
  `testSnapshotOmitsFieldClockKeysWhenAbsent`；自检 `L019` 6 项。
  （LESSON-020 定稿后，守卫改为 `L020` 组：透出 + 语义 + 不倒退 + 0 值 fail-closed。）
- **代价记录**：快照 385 KB → +77 KB（+20%）。
- **通用教训（两条，第二条更贵）**：
  1. **只要链路上存在「白名单 / 裁剪 / slim / 投影」这类中间层，就必须有一条
     端到端出口断言。** 分别测生产者写对、消费者读对，是**测不出中间人被删**的。
  2. **"消费者没拿到数据"不等于"消费者该拿到数据"。** 我按契约对称性推出"必须透出"，
     但漏查了**生产者写这个字段的频率是否配得上它的语义**。修 bug 前先问：
     **这个字段多久更新一次？读它的地方按什么频率判它？**
     一个"恒真但毫无信息"的字段，比"缺失"更危险——缺失会回退到保守分支，
     存在则会让下游**自信地用错基准**。
  同型错误在一个项目里出现两次，说明它是个**结构性陷阱**：
  凡是"值 + 时间"一起比较的地方，都要单独问一句"时间该不该独立推进"。

## LESSON-020 · 一个字段的时钟，必须由**供这个字段值的那个源**来推进

- **日期**：2026-09-14（LESSON-019 当晚根治）
- **背景**：LESSON-019 查出字段时钟到不了 T 板，直接透出却让 510050 灰行 40%→72%
  而回退。用户决定继续做对。
- **✅ 第一步先验前提，结果**证伪**了最自然的方案**：
  我本打算"TDX 每轮都重新观测 → 用 incoming 的 `time` 当字段观测时钟"。
  取证脚本 `scripts/probe_tdx_time_semantics.py` 实测：
  ```
  载荷未变时：时钟推进 0 次 / 时钟不动 13 次
  → TDX time = 「通达信缓存里这份快照多旧」，不是「我们何时观测到它」
  ```
  载荷变化时时钟必动、载荷未变时 13/13 都不动 —— **它本身就是 age，不能当观测时钟**。
- **真观测时钟是免费的**：daqmt 把 TDX 喂的数据合并进内存的**那一拍墙钟**
  （`TDX_OPT merge` 每轮约 1s）。这才是"我们观测到这条 TDX 数据"的时刻。
- **定稿口径（按字段的供给方分别计时）**：
  | 字段 | 供给方 | 时钟推进方式 |
  |---|---|---|
  | `bookTime`（五档） | TDX | 每轮 TDX 喂数 → 合并墙钟 |
  | `lastTime` | 谁的值新谁供 | 用**该字段自己的时钟**判断当前值是谁供的，是 TDX 才推进 |
  | `qtyTime` / `oiTime` | QMT（`optionTickMergeKeepQty` 会保住 QMT 值） | **绝不**跟 TDX 推进 |
  | `time`（公共） | — | 保留为无专属键记录的回退 |
- **为什么量仓绝不能跟 TDX 推进**：量仓是 QMT 的槽位（`qtyFromQmt`，实测
  510050=87/92、510300=44/98、510500=54/160、588000=90/166）。跟着 TDX 推进 =
  **用 TDX 的观测时刻给一个 TDX 没供的值背书** —— 正是 LESSON-019 教训 2 的形态。
- **写回测试抓到的第二个缺陷**：不倒退约束我第一版只加在 `last` 上，`book` 会被回拨，
  `testTdxMergeFieldClockNeverRewinds` 当场红。补齐后为**统一不倒退**（4 个字段都查）。
- **实测（部署后 3 分钟，与两次历史读数同口径对照）**：
  ```
  链        修改前基线   仅透出(翻车)   语义+透出(定稿)
  510050       13%          72% ❌          16% ✅
  159915        4%           —             9%
  510300       12%           0%             1%
  510500        8%           1%             1%
  588000       10%           4%             2%
  ```
  字段时钟 p50：`lastTime`/`bookTime` 3~8s（TDX 与实时），
  510050 的 `qtyTime` **26s**（QMT 轮转供给方，如实）。
- **守卫**：`L020` 共 13 项，**同时**钉住两件事（缺一即翻车）：
  ① 白名单透出 4 个键 + 公共 `time`/`stime` 仍在；② `optionTickStampTdxFieldClocks`
  存在且**两种落盘形状都被调用**；③ 量仓槽位不跟 TDX 推进的判据；
  ④ 6 条具名回归（推进/不推进 QMT 槽位/不倒退/两种形状/透出/0 值 fail-closed）。
- **通用教训（三条）**：
  1. **先验前提再动代码。** 这次的方案从"契约对称性"看完全成立，但一个 13 行的
     取证脚本就把它证伪了。凡是"某字段可以当 X 用"的假设，都要有一条实测。
  2. **问"这个字段归谁供"，而不是"谁在写它"。** 全链共用一个 `lastTime` 必然错：
     一张合约的 `last` 可能来自 QMT、盘口来自 TDX、量仓又是 QMT。
     **per-field as-of 的前提是 per-field 归属**。
  3. **顺序不能颠倒：先把时钟语义修对，再让它见人。** 先透出后修语义，
     用户看到的就是"变差了"——哪怕最终口径完全一样。
- **全天全程样本（收盘后补测，`_planA_probe.log` 13:00–14:55，680 条盘内样本）**：
  ```
  链         p10    p50    p90    max
  510050      4s     9s    16s    28s
  159915      3s     7s    13s    25s
  510300      7s    14s    23s    35s
  510500      3s     7s    18s    37s
  588000     12s    20s    28s    38s
  ```
  分段对照（按部署时刻）显示各版本 p50 都在同一量级，**没有任何版本退化**；
  逐 5 分钟中位全程平稳、**净漂移 ≈ 0.01~0.09s/样本 = 无累积**。
  唯一的 `max=5204s` 只出现在 **13:00:03 一条样本**上且五链同值
  = 11:33→13:00 的午休间隔（202 分钟）——**与"午休不刷新"完全吻合，是预期不是失效**。
- **又一次自我纠错（方法论）**：我曾在 13:05–13:09 这 5 分钟小窗里看到
  10→30→10 的规律数值，判定"存在约 30~60s 周期的锯齿"。全量量化后**证伪**：
  「三链完全相同」在低滞后样本里只占 **3%**，所谓"周期"是 10s 采样对 10s 中位的
  **混叠**，我的低点检测器抓到的是噪声。**窗口越短越容易看出"规律"——那往往是
  混叠，不是信号。** 判断周期性必须用足够长的序列 + 明确的周期检出器，不能目视一小段。

## LESSON-021 · 新鲜度判据必须带时段窗口——固定阈值在尾盘/盘后必然误报

- **日期**：2026-09-14（收盘前后的自检连续抓到 4 条**假 FAIL**）
- **症状**：方案 A 与字段时钟都已验证良好，但同一套自检在收盘前后突然红：
  ```
  14:57  510050 行数>0 且灰行<25%    gray≈24 (26%)          → FAIL
  14:59  510500/510300/588000 中位年龄<30s  中位 144.2s      → FAIL ×3
  ```
- **怎么判定是假 FAIL（不是"改阈值让它过"）**：两侧都量了**源侧自身**的新鲜度 ——
  ① 灰行：TDX **自己的** `time` 已 p50=**73s**、599/648 超 30s；桥接只是如实跟随；
  ② 中位年龄：三条链 min 仍有 **9s**（部分合约还在成交），而 14:52 中位仅 **65~109s**。
  两条都指向同一个事实：**收盘前合约陆续停止成交，值确实不动，页面确实该变灰。**
  这是行情的性质，不是服务的问题。
- **反例（为什么值得写下来）**：同一天更早的时候，一模一样的"灰行高"**是真问题** ——
  LESSON-019 那次的 510050 灰行 72% 是字段时钟语义错。**同一个数字，两种含义**，
  区别就在"源侧自己动不动"。所以判据不能只看下游比例，要看**源侧是否也在动**。
- **修法**：引入 `inCloseTailQuiet()`（14:45–15:00），`灰行<25%` 与 `中位年龄<30s`
  **共用**同一个窗口函数；窗口取右开（15:00 之后走既有的盘后分支，用
  `postCloseMaxAgeSec()`，它随"距最近收盘多久"自动放宽）。
  **窗口外判据完全不变** —— 白天出现同样比例仍然 FAIL（当天已实测会红）。
- **守卫**：`tests/test_selfcheck_time_windows.py` 4 条，自检 `L021` 4 项：
  ① 边界精确（**14:44 必须仍在窗口外**、14:45 进、15:00 出）；
  ② 窗口占交易时段比例 < 20%（防有人图省事放大成"整个下午"，把白天真问题一起盖掉）；
  ③ 两条判据必须共用同一函数（只改一条 → 另一条继续误报）；
  ④ `inTradingSession` 的 09:30/15:00 边界不得被带偏。
- **通用教训**：
  1. **任何"绝对阈值"判据都要问一句：这个量在时段边界上会怎么变？** 日内的新鲜度、
     成交量、活跃度全都有 U 形或收盘衰减，固定阈值必然在两端误报。
  2. **放宽判据前必须先证明"源侧也在变差"。** 只看到下游指标超标就调阈值，
     等于把 LESSON-019 那种真问题一起放走 —— 会变成"改测试让它过"。
  3. **同一条判据的两个分支（盘中/盘后）必须共享同一个时间函数**，否则改一处留一处。

## LESSON-022 · 字段级来源只能为实际字段值背书，空值不得继承整行来源

- **日期**：2026-09-14
- **症状**：`quote-delta` 中一张 TDX 合约没有 `oi/openInt/openInterest` 时，页面虽显示
  `—`，悬停来源却显示 `TDX`，容易被理解成“通达信给出了持仓量”。
- **错误写法**：`_optTDeltaField()` 无条件调用 `_optTDeltaSource()`；整张快照的
  `fromTdx` 被拿来给空的 OI 字段贴来源。
- **为什么错**：来源是“这一个数值由谁给出”的事实，不是“这条记录曾被谁合并过”的事实。
  TDX 原始期权快照没有可靠实时 OI，空字段继承来源会把缺失伪装成可追溯数据。
- **正确写法**：由 `sourceKnown` 绑定字段是否实际有数值（盘口绑定任一买一/卖一）。
  QMT/TDX 原始输入均用 `optionTickStampFieldSources()` 逐项标源；TDX 合并时若保留
  既有 QMT 的最新/量/仓，必须一并保留其来源与专属时钟。无值时返回 `source=None`，
  前端显示“未知”。
- **守卫**：`testLightDeltaDoesNotAttributeMissingOiToTdx`、
  `testTdxMergeKeepsQmtSourcesForQmtCarriedFields`、`testDirectQmtTicksStampFieldSources`，
  以及自检 `L022`。
- **通用教训**：数据质量元信息也必须逐字段建模。`来源/时间/精度` 与数值一样，
  不能从同一行其他字段或整条记录“借用”。

## LESSON-023 · 优先级容量不足必须显式降级，不能把已持仓合约静默放回长尾

- **日期**：2026-09-14
- **症状**：原 P0 规划把每链优先列表直接截为 `priorityPerUnderlying=3`。当真实开放仓位
  多于 3 张时，排在后面的仓位会落入普通长尾，日志仍看不出“持仓优先”已失效。
- **错误写法**：在加入开放仓位、ATM、活跃合约之后统一执行 `ordered[:perUndl]`。
- **为什么错**：固定 P0 槽位是吞吐约束，不是业务优先级的裁剪许可；静默裁剪既违反
  “持仓优先”，又令 SLA 监控无法暴露容量不够。
- **正确写法**：`priorityPerUnderlying` 仅是普通候选预算；所有开放仓位都保留在 P0 队列，
  使用 `max(perUndl, len(heldInChain))`。若 P0 超过可服务容量，既有 `p0_capacity`
  日志明确报 `DEGRADED`，不伪造保证。
- **守卫**：`testOpenPositionsAreNeverDemotedIntoTailWhenTheyExceedP0Slots`，以及自检 `L023`。
- **通用教训**：当资源预算与“必须优先”的业务集合冲突时，正确行为是保留集合并暴露降级，
  不是为了让吞吐统计好看而悄悄丢掉优先语义。

## LESSON-024 · 备用源必须在主源握手之前启动，否则“降级”只是纸面能力

- **日期**：2026-09-14
- **症状**：QMT 桥接端口 `15573/15574` 停止监听时，`15581` 的 TDX 快照仍有 648 张期权，
  但 `15580` 的 `opt` 与页面 `quote-delta` 都为 0。
- **错误写法**：主进程在 HTTP 起好后立即阻塞于 `waitUntilRpcPing()`，只在 QMT 成功握手后
  才启动包含 TDX 合并的期权线程。
- **为什么错**：把“QMT 主供”误实现为“QMT 是所有来源的启动前置条件”。这使 TDX 的独立性
  在最需要它的故障场景失效，也违背了页面必须可观测降级状态的要求。
- **正确写法**：QMT 等待期间先从本地 `opt_basic` 加载五链代码/要素，启动无 QMT RPC 的
  `TDX_FALLBACK` 循环并以 `forceTdx=True` 合并；桥接恢复后由事件停止该循环，再进入
  常规 QMT 主供 + TDX 兜底链路。若 TDX 也不可用则明确为空，不伪造行情。
- **守卫**：`testForcedTdxMergeCoversNominalQmtLedChain`、
  `testPrepareTdxFallbackLoadsAllFiveChainsFromOptBasic`、
  `testTdxFallbackPollOnceDoesNotTouchQmtRpc`、
  `testMainStartsTdxFallbackBeforeBlockingForQmtRpc`，以及自检 `L024`。
- **通用教训**：多源高可用不只看“代码里有 fallback 函数”；要验证故障发生时它已在运行，
  且不依赖失效主源的连接、锁或初始化步骤。

## LESSON-025 · 可用性自检必须区分“主源退化”和“已验证的降级服务”

- **日期**：2026-09-15
- **症状**：`15573/15574`（QMT 主桥）离线时，新的 `TDX_FALLBACK` 已在 `15580` 提供五条
  期权链，但自检仍把“主桥端口缺失”直接判成整套 T 板服务 FAIL，掩盖了真正需要区分的
  两件事：主源已退化，以及页面是否仍可用。
- **错误写法**：把某一主源端口等同于整个服务可用性，只检查监听状态，不检查实际降级
  快照的五链覆盖和字段级来源。
- **为什么错**：高可用架构中，主源故障不应被美化成健康，也不应把已经验证可交付的备用源
  一起报死。两种误报都会让运维人员看不到“该修主桥”与“用户当前能否继续看盘”的边界。
- **正确写法**：主桥在线时按 QMT 正常路径验收；主桥离线时只在 `5000/15580/15581` 都在，且
  `optMeta/opt` 对五条链均有记录、每条至少一个字段明确标为 `TDX` 时，判“核心服务可用
  （TDX 降级）”，并单列 `DEGRADED`/OI 未知。任一链或 TDX 端口缺失仍为 FAIL。
  跨交易日的盘外时段，旧 tick 被日期校验安全过滤而没有“当天字段”时，只报“盘外待市”
  SKIP；不得把它伪报成实时健康，也不得当作盘中故障。
- **守卫**：`tests/test_selfcheck_qmt_tdx_fallback.py` 四条，以及自检 `L025`。
- **通用教训**：可用性健康度至少要分三层报告：主源健康、降级可交付、数据字段能力。不能用
  单个端口或单个绿灯代替端到端服务结论。

## LESSON-026 · 主源字段陈旧时，备用源必须逐字段接管，不能被历史“主源锁”永久压制

- **日期**：2026-09-15
- **症状**：QMT 全推正常、TDX 每约 3 秒重新观测到盘口，但 `510300/510500/588000`

  `lastTime/qtyTime` 多旧，都压住 TDX 本轮的实际值。

  语义是有动态行情时回调推送；回调暂时沉默时，旧 QMT 字段不能比已经重新观测到该字段的
  TDX 更可信。反过来，TDX 没有可靠 OI，绝不能用它的墙钟给旧 `openInt` 贴“新鲜”标签。
- **正确写法**：在每次 TDX 合并拍点，以 `QMT_LED_MAX_STALE_SEC` 判定 **字段自己的**
  QMT 观测时钟。仅新鲜 QMT 的 `last/qty` 可保留；超过阈值且 TDX 实际提供该字段时，
  TDX 接管数值、来源和观测时钟。OI 始终保留 QMT 值与其真实 `oiTime`，等待 QMT 补丁。
- **守卫**：`testTdxTakesOverStaleQmtLastAndVolumeButNeverFakesOi`、
  `testTdxTakesOverStaleQmtSourceWhenValuesAreUnchanged`（包括“数值未变但来源必须交接”）和
  `testTdxAllowedWhenFreshBookMasksStaleQmtLastAndVolume`（TDX 的新 book 墙钟不能遮住 QMT 字段超时），以及
  `selfcheck_delivery.py` 的“QMT回调陈旧时TDX按字段接管”。
- **通用教训**：多源融合的优先级必须是 `字段 × 时间 × 可用性`，不能只是“哪条记录
  曾来自主源”。一条记录里 book、last、volume、OI 可以且应当由不同源分别背书。

## LESSON-029 · 回调刚收到不等于交易所行情刚发生

- **日期**：2026-09-15
- **症状**：两张沪市期权的 QMT 回调接收年龄只有 2–7 秒，但其交易所 `time` 已滞后约
  2,420 秒；外层聚合只按 `_recv_mono` 认定命中，因而将重复回放的旧 `openInt` 标成健康，
  OI 修复队列也不会及时触发。
- **错误写法**：把本地 callback 的到达时间当成行情事件时间；只要回调持续抵达，就认为
  `last/volume/openInt` 都是新鲜的。
- **为什么错**：回调链路可能重放终端缓存。到达时钟只能证明通信未断，不能证明交易所
  最后事件仍在推进；单纯扩大轮询数量会更快地读取同一条旧事件，不能修复 OI。
- **正确写法**：同时校验 receipt clock 与原始 `time/stime` 的交易所事件时钟，并要求为
  当日、事件年龄不超过 `OPT_QUOTE_CACHE_MAX_AGE_SEC`。外层聚合拒绝过期事件以触发既有
  分批重订；QMT 桥接缓存也按同一规则筛除，并将事件年龄透出用于诊断。没有可验证的新
  `openInt` 时保持其原有时间戳，绝不涂成实时。
- **守卫**：`testCallbackReceiptCannotMaskStaleMarketEvent`、
  `test_repeated_stale_market_event_is_not_a_live_callback`，以及
  `selfcheck_delivery.py` 的 L029 三项源码/回归守卫。
- **通用教训**：实时性必须分成「传输到达新鲜度」与「市场事件新鲜度」；两者缺一不可，
  并且字段级 SLA 应以市场事件时钟为准。

## LESSON-030 · 同一 QMT 策略内不能用 OI 补丁挽救已静默的行情回调

- **日期**：2026-09-15

- **正确写法**：TDX 盘口合并始终继续；仅当全推健康时运行 QMT OI P0/P1 补丁。进入

- **守卫**：`testQtyPatchYieldsWhenWholeQuoteIsStale`、
  `testQtyStopsWhenQuoteDeadYield`，以及 `selfcheck_delivery.py` 的 L030 门控守卫。
- **通用教训**：单线程上游的恢复优先级高于补数；“数据缺失”不能用会阻塞数据源本身的
  请求来修复。真正同时保证两者须采用独立数据桥接。

## LESSON-033 · 订阅 RPC 的快速 ACK 不是“空订”的证据

- **日期**：2026-09-15
- **症状**：外层行情进程重启后，`subscribe_whole_quote` 在 20--170ms 内返回；旧启动逻辑
  将此直接视为 `SUBSCRIBE_NOOP`，反复退订重订并等待约 106 秒，最后保留同一类快速 ACK 后
  才开始期权线程。随后全推实际正常到达，`unique` 从 5,099 升至 7,097。
- **错误写法**：用一次 RPC 的返回耗时判定 callback 一定不会到达，并在没有 callback 观察窗口
  前主动撤销刚收到的订阅句柄。
- **为什么错**：桥接可以异步接受订阅、随后才开始分发 callback；RPC ACK 的时长只能作为诊断
  信号，不能替代以 `lastPush/unique/silence` 为依据的健康判定。
- **正确写法**：启动期保留所有成功返回的订阅句柄；快速 ACK 只记录 `SUBSCRIBE_FAST_ACK`。
  看门狗在实际静默超过门限时再进行受控退订重订和回调确认。
- **守卫**：`testFastSubscribeAckIsKeptForWatchdogConfirmation`，以及
  `selfcheck_delivery.py` 的 L033 源码/回归守卫。
- **通用教训**：异步系统中“请求已受理”“数据已回调”“数据已新鲜”是三件不同的事，
  必须以对应层级的证据分别判定。

## LESSON-055 · 后台整表不得叠请求堵死 quote-delta

- **日期**：2026-09-23
- **症状**：顶栏/盘口「有数但几乎不跳」；观测时钟停在几分钟前；最新格没有
  `data-opt-quote-observed-at`。
- **错误写法**：`backgroundRefreshTick` 无 inflight，6s 定时器在整表未返回时继续
  `fetch`；`loadUnderlying` 同标的静默刷新也 `quoteDeltaSeq++`。
- **为什么错**：浏览器对 localhost HTTP/1.1 只有约 6 条连接。未完成的整表请求

  （排队时 abort 会自杀重试、更堵）；
  首屏先发 quote-delta 再整表；仅切标的时才 bump `quoteDeltaSeq`。
- **守卫**：`test_opt_t_quote_delta_not_starved_by_board_refresh`，以及自检 L055。
- **通用教训**：轻量实时通道必须比后台重算更优先占用连接；定时器没有 inflight
  上限，或给被高优先级持续压后的低优先级请求加 abort 重试，都会在请求变慢时
  自我放大成雪崩。

## LESSON-068 · 历史 Flow 的缺失值必须先保留 null 语义再格式化

- **日期**：2026-10-04。
- **症状**：rt_monitor 重启后自己的日志全部消失，实际被写进了 `opt_vertical_spread_backtest.log`；pytest 跑一次就往 `logs/` 正式日志里灌入测试用例的 Traceback（含假口令字符串）。

- **通用教训**：全局单例（根日志器、信号处理、locale、全局 session）只能由进程入口配置，库/被导入模块不得改写；测试进程本身就是宿主，必须证明它不留生产副作用。

## LESSON-086 · 单实例 auto-kill 不得把自己的启动器当成旧实例

- **为什么错**：venv 转发器先于真解释器创建、命令行相同，二者间隔偶尔超过 10ms 就被误杀，作业对象随即连带杀死本进程——是时序竞态，平时多数能过，所以长期潜伏。ProcessPool 子进程不会随父进程被强杀而退出。

## LESSON-087 · 抽出共享模块后，凡「单文件拷贝」的地方都会缺依赖

- **通用教训**：给文件新增依赖时，「能 import」只证明了仓库内的一种运行方式；还要枚举所有把它脱离仓库单独运行的方式。


## LESSON-088 · 优化路径因输入格式不符而静默失效，回退分支让结果「正确但没变快」

## LESSON-089 · 覆盖率体检的基准被「双代码 / 已退市 / 未上市」污染，误报成数据缺失

- **日期**：2026-10-04。
- **症状**：`data_health_check.py` 第一版报告 fina_quarter_metrics 缺约 128 只、财报类多张表都缺几十只；逐只核对后，大部分是基准本身的问题，不是数据缺失。
- **错误写法**：拿「income 里该报告期出现过的 ts_code」直接当分母。里面混入了北交所换代码后的旧代码（新旧两个代码各报一次）、已退市但 income 仍有记录的股票、报告期末之后才上市的股票；金融业也被算进了一张本来就不计算金融业的衍生表。
- **为什么错**：基准表与被检表的口径不一致，算出的缺失率反映的是口径差，而不是同步质量。
- **正确写法**：基准 = income 该期出现 **且** `stock_basic.list_status='L'` **且** `list_date <= 期末` **且** 不是北交所陈旧旧代码（`STALE_BJ_SQL`）；衍生表按表声明排除行业（`anchorExcludeIndustry`）。缺失清单要**抽样查原因**后再下结论。
- **守卫**：交付自检 L089（`ANCHOR_SQL` 必须同时含这三个条件；`fina_quarter_metrics` 必须声明排除金融业）。
- **通用教训**：覆盖率 = 实际 ÷ 应有。「应有」那一侧的口径错了，再精确的计数也没意义；先抽样核对缺失项的真实原因，再定基准。


## LESSON-090 · 用 PowerShell 往文件追加中文，会写出非法 UTF-8

- **日期**：2026-10-04。
- **症状**：第 2 轮给 `.gitignore` 追加的中文注释，在 `git diff` 里显示为乱码加 `?`；用 GBK 解码也失败，因为中文字节已被截断。规则行本身仍生效，所以没有任何报错。
- **错误写法**：在 Windows PowerShell 5 里用 `Add-Content` / `>>` / `Out-File` 写入含中文的内容（默认编码随命令和系统区域设置而变）。
- **为什么错**：同一个文件里前几行是 UTF-8，新追加的行按另一种编码写入，或在管道里已被替换成 `?`。坏掉的只是注释，不影响功能，所以只有人去读时才会发现。
- **正确写法**：凡是含非 ASCII 的文本文件，一律用 Python 按字节写（`Path.write_bytes(text.encode('utf-8'))`）或用编辑工具写，**不要用 PowerShell 写**；写完用严格 UTF-8 解码复核。
- **守卫**：交付自检 L090（`.gitignore`、`AGENTS.md`、`jinwq.mdc`、`LESSONS.md` 等关键文本文件不得含 UTF-8 替换字符）。
- **通用教训**：只写注释的改动也要回读校验；「功能没坏」不等于「文件没坏」。
